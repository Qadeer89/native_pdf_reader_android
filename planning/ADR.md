# Architecture Decision Record — Vertical Slice (Phase 1), Reader MVP (Phase 2) and the Phase 3 engine gate

Scope: decisions needed to produce a compiling, testable vertical slice (app shell, open a PDF, render a page), the Phase 2 reader-navigation increment (SAF/share-intent open, next/previous page, pinch-zoom, thumbnails, recents), and the Phase 3 PDF-engine proof-of-concept gate. The engine *decision itself* (which SDK ships in the app) is a licensing/cost call for the user/business, recorded as DEC-001 in `docs/DECISIONS_AND_OPEN_QUESTIONS.md`, not decided unilaterally here — this file records what was built and tested to produce the evidence that decision needs.

## ADR-001 — minSdk / targetSdk / compileSdk for the slice
- Status: Proposed (needs product sign-off per `docs/DECISIONS_AND_OPEN_QUESTIONS.md`)
- Decision: `minSdk = 26` (Android 8.0), `targetSdk = 34`, `compileSdk = 34`.
- Rationale: `android.graphics.pdf.PdfRenderer` (used for baseline rendering, PDF-002) has existed since API 21, but API 26 covers >98% of active devices (per Android Studio distribution data at time of writing — reverify before release) and lets us use modern Compose/Material3 and `ContentResolver` APIs without excessive compat shims. This is a starting point for the vertical slice only; final minSdk is still an open decision (see Open Questions).
- Consequences: no API 21-25 support; revisit if a lower floor is required by stakeholders.

## ADR-002 — Vertical-slice PDF rendering: Android `PdfRenderer`
- Status: Proposed for Phase 1/2 only. Does NOT satisfy the engine-selection gate in `docs/ARCHITECTURE.md` §2.
- Decision: Use the platform `android.graphics.pdf.PdfRenderer` behind a `core:pdfengine` adapter interface (`PdfEngine`) to open a document and render page bitmaps for the vertical slice.
- Rationale: Zero license cost, zero extra dependency, sufficient to prove the open→render path end-to-end and unblock UI/architecture work. `PdfRenderer` cannot do annotations, page merge/reorder, forms, or signing — those require the separate PDF-engine proof-of-concept mandated by `docs/ARCHITECTURE.md` §2 before PDF-005/006/007/008/009 are implemented.
- Consequences: the `PdfEngine` interface is designed so the platform renderer can be swapped for (or composed with) a commercial/open-source engine later without changing call sites in `feature:reader`.
- Open follow-up: commercial-SDK POC (Apryse/Nutrint) vs. vetted open-source combination, per `docs/ARCHITECTURE.md` §2 and `docs/DECISIONS_AND_OPEN_QUESTIONS.md`.

## ADR-003 — Dependency injection: manual DI for the slice
- Status: Proposed.
- Decision: Use manual constructor injection via a small `AppContainer` for Phase 1. Defer Hilt adoption until module count justifies it (per `docs/ARCHITECTURE.md` §1: "Hilt for multi-module app, or manual DI for a small MVP").
- Consequences: migration to Hilt is mechanical later; no behavior depends on it yet.

## ADR-004 — Module layout for the slice
- Status: Proposed.
- Decision: Start as a single Gradle module (`app`) containing the slice's UI, a `pdfengine` package (adapter + platform implementation), and a `model` package, rather than pre-splitting into the full module list in `docs/ARCHITECTURE.md` §3. Package-level boundaries (`com.pdfreader.app.pdfengine`, `com.pdfreader.app.model`, `com.pdfreader.app.reader`) mirror the eventual module names so extraction to Gradle modules (`core:pdfengine`, `core:model`, `feature:reader`) is a low-risk refactor once annotation/pageops/signature/cloud features arrive and justify the build-time cost of multi-module separation.
- Rationale: avoids premature multi-module ceremony for a one-screen slice while keeping the eventual boundaries visible in the package structure.

## ADR-005 — UI toolkit and architecture pattern
- Status: Confirmed per `docs/ARCHITECTURE.md` (not a new decision).
- Decision: Jetpack Compose + Material 3, single-Activity, MVVM/UDF with `ViewModel` + `StateFlow`.

## ADR-006 — Test strategy for the slice
- Status: Proposed; adjusted for this environment (see note).
- Decision: One JVM-executable smoke test using Robolectric (`org.robolectric:robolectric`) that opens a bundled fixture PDF from app assets through the `PdfEngine` adapter, renders page 1, and asserts a non-empty bitmap of the expected dimensions. Robolectric lets `./gradlew testDebugUnitTest` actually execute this against a simulated Android environment without a device/emulator.
- Environment note: no Android emulator or physical device is available in this execution environment (no AVD images, no connected device). A true instrumented test (`androidTest`, run via `connectedAndroidTest`) could not be executed here and must not be reported as passing. The Robolectric unit test is the automated smoke test actually run and verified in this pass; a real-device/emulator instrumented test is carried forward as backlog (see `IMPLEMENTATION_BACKLOG.md`).
- Rationale: satisfies `MASTER_PROMPT.md` workflow step 3 ("plus one automated smoke test") and step 9 ("Never claim tests passed unless executed") simultaneously — the test is both automated and actually runnable in this environment.

## ADR-007 — Opening SAF/share-intent documents without an app-private copy
- Status: Decided (Phase 2).
- Decision: `PdfEngine.open` takes a `PdfSource` (`LocalFile` or `ContentUri`). For `ContentUri`, `PlatformPdfRendererEngine` resolves a `ParcelFileDescriptor` directly via `ContentResolver.openFileDescriptor(uri, "r")` rather than copying the picked document into app-private cache first.
- Rationale: `ContentResolver.openFileDescriptor` already returns a real, seekable file descriptor that `PdfRenderer` can use directly; copying would add latency/disk usage for every open with no benefit for a read-only viewer. `AssetPdfCopier`'s copy-to-cache path is kept only for the bundled asset fixture, which has no other way to get a real file descriptor (assets are not directly exposed as `content://` Uris).
- Consequences: no byte-for-byte app-private copy of user documents exists for the reader path, which is good for docs/SECURITY_PRIVACY.md §4 ("preserve source file on failures... never overwrite silently") since we never touch the source. Page operations/signing (Phase 3/4) that need to *write* a new file will still go through "write to temp, validate/reopen, then commit" per the same doc, independent of this read path decision.
- Permission handling: `MainActivity.takePersistableReadPermission` calls `takePersistableUriPermission` for SAF-picked Uris (best-effort; share/view-intent Uris are not always grantable and failure there is expected/non-fatal, per Android's documented behavior for those intent types).

## ADR-008 — Recent documents: Room, metadata-only, excludes the bundled fixture
- Status: Decided (Phase 2).
- Decision: `data/recents` (`RecentDocumentEntity`, `RecentDocumentDao`, `RecentDocumentsDatabase`, `RecentDocumentsRepository`) stores only `uri` (primary key), `displayName`, `pageCount`, and `lastOpenedAtEpochMillis` — never document bytes, per docs/ARCHITECTURE.md §1 ("avoid storing PDF bytes in database by default"). `ReaderViewModel.openSource` only calls `recordOpened(...)` for a real `PdfSource.ContentUri` open; the bundled fixture (always opened on startup via `PdfSource.LocalFile`) is never recorded, since it isn't a real user document and would otherwise pollute "Recent" on every launch.
- Display name/size come from `ContentResolverDocumentMetadataResolver` (`data/documents`), which queries `OpenableColumns.DISPLAY_NAME`/`SIZE` and falls back to the raw Uri string on any failure — never trusts a Uri's path segments as a filename, per docs/SECURITY_PRIVACY.md §1.
- Consequence/finding: Room's `@Query`-returned `Flow` delivers invalidation callbacks from Room's own background executor, which then post the resumption of whatever coroutine is collecting that Flow back onto its original dispatcher. When that collector runs on `Dispatchers.Main.immediate` (as `ReaderViewModel.recentDocuments`'s `stateIn` does) and the test harness is Robolectric with its default *paused* main Looper, that posted resumption sits in the queue until something pumps it (`shadowOf(Looper.getMainLooper()).idle()`) — a real device's live main Looper has no such issue. `PdfReaderViewModelSmokeTest`'s recents test accounts for this by polling with an explicit `idle()` call rather than asserting immediately after a write; this is a test-environment detail, not an app bug, but is worth knowing before writing further Room-flow-backed tests. `recentDocuments` itself uses `SharingStarted.Eagerly` (not `WhileSubscribed`) specifically so reading `.value` directly — in tests or anywhere else — reflects the live query rather than a frozen seed value.
- `exportSchema = false` for now (version 1, no migrations yet); revisit once a schema migration is actually needed.

## ADR-009 — Phase 3 PDF-engine POC: PDFBox-Android, testImplementation-only
- Status: POC complete; engine selection itself is **not decided here** — see DEC-001 in `docs/DECISIONS_AND_OPEN_QUESTIONS.md`.
- Decision: Added `com.tom-roush:pdfbox-android:2.0.27.0` as `testImplementation` only (`app/build.gradle.kts`) — explicitly *not* `implementation`, so it does not ship in the app before DEC-001 is approved. Wrote `app/src/test/java/com/pdfreader/app/poc/PdfBoxAndroidEnginePocTest.kt` to exercise the three `docs/ARCHITECTURE.md` §2 required-POC scenarios that are actually reachable without a device or a business decision: annotate/save/reopen round trip, merge, and encrypted-PDF open/reject. All 3 pass under `./gradlew testDebugUnitTest`.
- Why this candidate and not the commercial ones: Apryse and iText both require either a sales/trial engagement or an AGPL-vs-commercial licensing call — decisions this agent does not make unilaterally (see MASTER_PROMPT.md "Security release blockers" / general operating constraints on account creation and purchases). PDFBox-Android (Apache 2.0) was the only candidate that could be integrated and actually tested in this pass.
- Why this POC runs fine under Robolectric when the `PdfRenderer`-based tests could not (see ADR-006): PDFBox-Android's document/annotation/encryption model (`COSDocument`, `PDDocument`, `PDAnnotation`, `StandardProtectionPolicy`, etc.) is largely pure-JVM ported code from Apache PDFBox — it doesn't route through Android's native graphics stack the way `PdfRenderer` does, so there's no native-binding gap for Robolectric to fall through.
- Consequences: if DEC-001 is approved, next steps are (a) promote to `implementation`, (b) extend the `PdfEngine` adapter (or add a sibling interface) for annotation/page-ops calls so `feature:annotations`/`feature:pageops` don't depend on PDFBox types directly, (c) run a malformed-PDF corpus pass before trusting it on untrusted user documents, (d) separately vet a signing path (BouncyCastle) before PDF-008. If DEC-001 is instead decided toward a commercial SDK, this POC code is deleted, not adapted — it was written to produce evidence, not to become production scaffolding by default.

## ADR-010 — PDF-005 annotations: two independent engines, tap-to-place note, export-as-copy
- Status: Decided (Phase 3, first increment), following DEC-001's approval.
- Decision: `PdfEditEngine` (`PdfBoxEditEngine`) is a *separate* interface/implementation from `PdfEngine` (`PlatformPdfRendererEngine`), not a merge of the two. `ReaderViewModel` opens both against the same `PdfSource` whenever a document is opened; `pdfEngine` still drives every page render, `pdfEditEngine` only tracks annotations until export. The rendered bitmap does **not** live-update when an annotation is added — `ReaderUiState.Loaded.annotationMarkers` carries normalized (0f..1f) marker positions for the current page, drawn as a simple Compose `Canvas` overlay (red dots) instead.
- Why not merge the engines: `docs/ARCHITECTURE.md` §2 explicitly warns not to combine engines until round-trip compatibility is proven — proven in the POC, but "proven compatible" and "safe to treat as one engine with shared state" are different claims. Keeping them structurally separate means a `PdfRenderer` rendering bug can never corrupt a PDFBox-held document and vice versa.
- Tap-to-annotate UX: `ZoomablePdfPage` gets a new `annotateMode` flag. While on, pinch-zoom/pan is disabled and a tap places a note at that fraction of the page; this avoids reconciling a transform gesture detector with a tap gesture detector on the same pointer input scope in one pass. Tracked as a backlog follow-up if simultaneous zoom+annotate turns out to matter.
- Export, not in-place save: `MainActivity` uses `ActivityResultContracts.CreateDocument("application/pdf")`, never an in-place overwrite of the opened document — matches `docs/PRODUCT_REQUIREMENTS.md` "Product principles" ("Preserve originals by default; no silent overwrites") directly, not just the write-temp-then-commit mechanics. `PdfEditEngine.writeValidatedTempCopy()` writes to an app-private temp file, reopens it to confirm the page count still matches, and only *that* validated file is ever handed to `DestinationWriter` for the actual commit — satisfying docs/SECURITY_PRIVACY.md §4's "write to temporary files, validate/reopen, then atomically commit."
- A real finding, not hallucinated: `./gradlew :app:dependencies` confirms PDFBox-Android transitively pulls in BouncyCastle (`bcprov`/`bcpkix`/`bcutil-jdk15to18:1.72`) — not declared directly, discovered by actually running the dependency report rather than assumed. Recorded in `planning/DEPENDENCY_LICENSE_INVENTORY.md`; relevant to PDF-008 planning since a signing-capable crypto library is now already on the classpath, though using it directly for signing still needs its own review pass.
- Not done in this increment (tracked in `planning/IMPLEMENTATION_BACKLOG.md`): custom note text entry (fixed "Note" text for now), annotation removal/undo, highlight/underline/other annotation *types* beyond a text note, and continuous-mode annotating.

## ADR-011 — PDF-006 page operations: staged edits, rebuild-the-tree reorder, verified API before coding
- Status: Decided (Phase 3, second increment).
- Decision: Extended `PdfEditEngine`/`PdfBoxEditEngine` with `rotatePage`, `deletePage`, `movePage`, `appendDocument` (merge), and `pageCount()`. Before writing any of this, actually decompiled `pdfbox-android-2.0.27.0.aar`'s `classes.jar` with `javap` to confirm the real `PDPageTree`/`PDPage`/`PDDocument` method signatures (`insertBefore`/`insertAfter`/`remove`/`add`/`getRotation`/`setRotation`/`importPage`/`removePage`) rather than guessing from memory of the Java PDFBox API — worth calling out because guessing wrong here would have produced code that compiles against a mocked assumption and fails at runtime in a way unit tests might not catch if the fake engine doesn't mirror the real one closely.
- `movePage(fromIndex, toIndex)`: implemented by converting the page tree to a plain `List<PDPage>`, doing an ordinary list move, then removing and re-adding every page in the new order — not by chaining `insertBefore`/`insertAfter` calls against a tree whose indices shift as you go. Simpler to get right; page counts in this app's scale make the extra churn irrelevant.
- Rotation gets **live visual feedback** without touching `PdfEngine`/`PdfRenderer` at all: `ReaderUiState.Loaded.pageRotationDegrees` is a pure Compose `Modifier.rotate()` on top of the already-rendered bitmap. This is safe specifically *because* rotation doesn't change page count or order — unlike delete/move/merge, there's nothing for the two engines' views of the document to disagree about.
- Delete/move/merge do **not** get live feedback: they change page count/order, and `pdfEngine` is still rendering the original, unedited file. Rather than attempting to keep two independent engines' page indices synchronized live (fragile, and not something a quick pass could verify is correct), these operations are "staged": applied to `pdfEditEngine`'s in-memory document, reported via a snackbar (`pageOpMessage`) saying the change needs an export to be saved, and only visible for real once the user exports a copy and reopens it. This is an explicit, documented scope decision, not a bug.
- Merge UX: reuses the existing SAF document picker (`ActivityResultContracts.OpenDocument`) for "pick a PDF to merge in," wired to `ReaderViewModel.mergeDocument(uri)` → `PdfEditEngine.appendDocument(PdfSource.ContentUri(uri))`. The picked document is opened and closed independently inside `appendDocument` — it is never left open or mutated, and the currently-open document's edit session is unaffected if the picked file fails to load.
- Not done in this increment (tracked in `planning/IMPLEMENTATION_BACKLOG.md`): a reorder UI (drag-to-reorder on the thumbnail strip) — `movePage` has an engine method and a test, but nothing in the UI calls it yet; insert-at-position (as opposed to always-append) and extract-to-new-file; preview/progress/cancellation for merge (fine for a 1-3 page fixture, would matter on a real large document).

## ADR-012 — PDF-007 visual signatures: not gated behind DEC-001/digital-signature decision, image-stamp via PDFBox, local-only storage
- Status: Decided (Phase 4, first increment).
- Decision: Visual signatures do **not** need a new engine/library decision. `docs/DECISIONS_AND_OPEN_QUESTIONS.md`'s "Required decisions" list only gates *certificate-based* signing (PDF-008) behind the digital-signature profile open question — a visual signature is just a stamped image, which the already-approved PDFBox-Android engine (DEC-001) draws directly via `PDPageContentStream`'s `drawImage`. Confirmed the relevant API (`PDImageXObject.createFromByteArray`, `PDPageContentStream`'s `AppendMode.APPEND` constructor + `drawImage(image, x, y, width, height)`) with `javap` against the real `.aar` jar before writing `PdfEditEngine.addImageStamp`, same practice as ADR-011.
- Local-only storage, per the "private local storage, excluded from sync by default" requirement: `LocalFileSignatureRepository` (`data/signatures`) stores signatures as PNGs under the app's private `filesDir` — never SAF, never a content provider. `AndroidManifest.xml` already sets `android:allowBackup="false"`, which already covers "excluded from sync by default" (no Android auto-backup happens at all, for any app data) — a separate `dataExtractionRules.xml` isn't needed for this requirement specifically; it stays a cross-cutting lint item for if/when `allowBackup` is ever turned on. No cloud sync exists yet regardless (Phase 5 is still gated).
- Creation UX: a signature can be drawn (finger strokes on a Compose `Canvas`, replayed onto an `android.graphics.Canvas`/`Paint` to produce the saved bitmap), typed (rendered via `Typeface.create(SERIF, ITALIC)`), or imported (picked image via `ActivityResultContracts.GetContent`, decoded through a new `ImageUriDecoder` abstraction — mirrors the existing `DocumentMetadataResolver`/`DestinationWriter` pattern of keeping `ContentResolver` calls behind a small interface rather than handing the ViewModel a raw `Context` — and downscaled to at most 800px on its longest side before saving, since a signature stamp never needs full photo resolution).
- Placement follows the PDF-005 pattern, not the PDF-006 one: stamping an image only changes a page's *content stream*, not its page count/order, so — like note annotations, and unlike delete/move/merge — it gets a live Compose overlay (`ReaderUiState.Loaded.signatureStamps`) instead of only a staged snackbar. One deliberate deviation from PDF-005's own overlay: a placed signature stamp is drawn whenever present, not only while "placement mode" is active (annotation markers are only drawn while `annotateMode` is on) — a signature is a real edit the user would otherwise think had vanished on leaving placement mode, where a note marker is more of an in-progress editing aid.
- Height is always derived from the stamped image's own pixel aspect ratio (`widthFraction` is the only size input `PdfEditEngine.addImageStamp` takes) — avoids ever stretching a signature, and avoids needing the ViewModel/UI to separately track a height fraction.
- Not done in this increment (tracked in `planning/IMPLEMENTATION_BACKLOG.md`): background removal/trimming for an imported photo of a signature, undo for a single placed stamp, remembering a per-document placement/size default, and the signature-recovery-across-reinstalls open question (still open — purely local storage has no recovery story).

## ADR-013 — PDF-008 signing-engine POC: PDFBox external-signing + BouncyCastle CMS, confirmed working
- Status: Decided (Phase 4, DEC-002 gate POC).
- Decision: `PdfSignaturePocTest` proves the mechanics DEC-002 proposed actually work: `PDDocument.addSignature(PDSignature)` + `saveIncrementalForExternalSigning(OutputStream)` → `ExternalSigningSupport` (confirmed present in `pdfbox-android-2.0.27.0` via `javap`, same practice as ADR-011/012) hands back exactly the bytes that need signing; a detached CMS/PKCS#7 signature built via BouncyCastle's own `CMSSignedDataGenerator`/`JcaContentSignerBuilder`/`JcaSignerInfoGeneratorBuilder` (no hand-rolled ASN.1) gets fed back via `ExternalSigningSupport.setSignature(byte[])`; reopening the signed file and re-extracting the signed content via `PDSignature.getSignedContent(bytes)` reproduces byte-for-byte what was actually signed (verified independently by hashing both sides); and `JcaSimpleSignerInfoVerifierBuilder` correctly verifies the real signature and correctly rejects a single flipped byte.
- A real, non-obvious finding from running this on this project's actual Robolectric setup, not assumed: BouncyCastle throws `CMSSignerDigestMismatchException` (a `CMSException`) when asked to verify a signature against content that doesn't match what was actually signed — it does **not** return `false` for that case the way a plain cryptographic-signature failure does. `verifyCmsDetached`'s tamper-detection assertion only works because it explicitly catches `CMSException` and treats it the same as a `false` verification result; a caller that doesn't expect this will see an uncaught exception instead of a boolean "invalid signature," worth remembering for the real `PdfEditEngine` verification code.
- A second real finding, this time about the test environment rather than the signing logic: Robolectric 4.13 transitively depends on `org.bouncycastle:bcprov-jdk18on:1.78.1` (its own test infrastructure), which collided on the unit-test classpath with the `bcprov/bcpkix-jdk15to18:1.72` that PDFBox-Android brings as this app's actual production dependency — same Java package (`org.bouncycastle.*`), different artifact, so Gradle doesn't dedupe them, and mixing both versions' classes at runtime threw `NoSuchFieldError` from BC's own static initializers. Confirmed via `./gradlew :app:dependencies --configuration debugRuntimeClasspath` that only the `jdk15to18` variant ever reaches the shipped app (the collision is test-classpath-only); fixed with a scoped `exclude(...)` on the `testImplementation(libs.robolectric)` dependency in `app/build.gradle.kts`, not by touching the production dependency.
- Not covered by this POC (left for the real implementation increment, tracked in `planning/IMPLEMENTATION_BACKLOG.md`): Android Keystore key generation/access, PKCS#12 file parsing on Android, any UI, and the revocation/trust-anchor disclosure DEC-002 requires. A self-signed, in-memory-generated certificate stood in for both of DEC-002's proposed key sources purely to exercise the PDFBox+BouncyCastle signing/verification path itself.

## ADR-014 — PDF-008 real implementation: sign-a-snapshot, two separate key-source packages, BC for PKCS12
- Status: Decided (Phase 4, third increment), building on DEC-002 and ADR-013's POC.
- Decision: `PdfEditEngine.signWithDetachedCms(signerName, privateKey, certificateChain)` is the production version of ADR-013's proven POC mechanics. It does **not** mutate `PdfBoxEditEngine`'s live `document` field — it takes an in-memory snapshot (`document.save(ByteArrayOutputStream)`), loads that snapshot as a *separate* `PDDocument`, signs that, and leaves the original `document` untouched and still open for further edits. This matters because PDFBox's incremental-signing save (`addSignature` + `saveIncrementalForExternalSigning`) is a one-shot, terminal operation on whichever `PDDocument` it's called on — mutating the shared engine instance in place would leave it unusable for anything else afterward (e.g. the user rotates a page, then decides to sign, then wants to rotate another page). Verified by a dedicated test (`signWithDetachedCmsProducesAValidatedSignedCopyAndLeavesTheLiveDocumentUsable`) that calls `rotatePage` on the live engine *after* signing and asserts it still succeeds.
- DEC-002's two signing-key sources are implemented as two genuinely separate types in their own `com.pdfreader.app.signing` package, not a shared abstraction with branches — `SigningIdentityManager` (Android Keystore, device-bound, hardware-backed; a key never leaves the Keystore, `loadSigningMaterial` hands back a Keystore-backed `PrivateKey` reference, not raw bytes) and `Pkcs12SigningMaterialLoader` (decrypts a user-provided .p12/.pfx file only in memory, for the duration of one signing call — the password is a `CharArray`, cleared from the ViewModel's hands as soon as it's been used, never logged or stored). This mirrors DEC-002's explicit requirement that these ship as two distinct features.
- Resolves DEC-002's flagged open gap ("verify the exact Android API level for PKCS12-related APIs") by not depending on Android's own PKCS12 support at all: `BouncyCastlePkcs12SigningMaterialLoader` explicitly requests `KeyStore.getInstance("PKCS12", BouncyCastleProvider.PROVIDER_NAME)` — this project's own bundled BouncyCastle provider (already registered for CMS signing, ADR-013), not whatever PKCS12 `KeyStore` implementation the OS happens to expose. Since this is pure `java.security` API with no Android-Keystore-specific calls, it has real unit test coverage (`Pkcs12SigningMaterialLoaderTest`, 3 tests, building an actual in-memory PKCS#12 file rather than a fake) — unlike the Keystore identity path, which cannot be exercised under Robolectric (no real "AndroidKeyStore" provider on the host JVM) and is covered only by a fake in `PdfReaderViewModelSmokeTest`.
- UI: a "Digitally sign" menu, kept structurally separate from PDF-007's "Sign" (visual signature) menu — same screen, same `ReaderScreen.kt`, but a different `TextButton`/`DropdownMenu` pair, not a shared one with a mode switch. This is a deliberate choice, not an oversight: `docs/SECURITY_PRIVACY.md` §5 requires visual signatures be clearly labeled as appearances only, and conflating the two menus risks a user not realizing which kind of "signing" they just did. The menu's required DEC-002 disclosure ("no revocation or timestamp checking in this version") is a disabled header item — same pattern already used for PDF-007's "appearance only" disclaimer (ADR-012).
- `MainActivity` shares one `signDestinationLauncher` (`CreateDocument`) between both signing flows (Keystore identity and PKCS#12) via a small `PendingSignAction` sealed class set right before launching it — simpler than two near-identical launchers, since only one signing operation is ever in flight at a time.
- Not done in this increment (tracked in `planning/IMPLEMENTATION_BACKLOG.md`): verifying someone else's signature when opening a PDF (only the "sign" half of PDF-008 exists so far, not "validate"), timestamping, revocation checking, a certificate preview before signing with an imported PKCS#12 file, and any real-device confirmation that a signed PDF actually renders as signed in a real-world viewer.

## ADR-015 — PDF-008 "validate": re-read raw source bytes, self-consistency only, never "trusted"
- Status: Decided (Phase 4, fourth increment), completing PDF-008's other half (ADR-014 built "sign").
- Decision: `PdfEditEngine.verifySignatures()` checks every `PDSignature` already present in the currently-open document and reports a `SignatureVerificationResult` per signature: whether the embedded CMS signature's bytes actually match the signed content and certificate (via BouncyCastle's `JcaSimpleSignerInfoVerifierBuilder`, same vetted-library approach as signing), whether the certificate's own `notBefore`/`notAfter` window covers right now, and whether the signature's byte range reaches the end of the file (`coversEntireDocument` — false means something was appended after this signature, which this signature's own check says nothing about).
- Re-reads the *source's raw bytes* (`PdfBoxEditEngine.readSourceBytes`, re-opening the original `File`/content Uri) rather than calling `document.save(ByteArrayOutputStream)` to get bytes to verify against — PDFBox's save path can reformat/re-serialize the document, which would silently break byte-range-based signature verification (the whole mechanism depends on the signature covering *exact* original bytes). A new `currentSource: PdfSource?` field tracks what to re-read, set in `open()` and cleared in `close()`.
- Deliberately **not** claiming trust: no certificate chain validation beyond the single leaf certificate's own expiry, no revocation (OCSP/CRL) check, no timestamp verification, and no app-curated trust-anchor/root-CA list — matching DEC-002's approved scope and `docs/SECURITY_PRIVACY.md` §5's "state limitations for revocation, timestamp and trust-anchor checks." `SignatureVerificationResult`'s own doc comment and the UI's "Signatures" status dialog both say this explicitly — a result here is "internally consistent," never "trustworthy."
- Computed once per document open (`ReaderViewModel.openSource`), not staged or session-only like PDF-005/006/007's edit features — it reports what's already, actually in the file, so there's nothing to "stage." Exposed via `ReaderUiState.Loaded.signatureVerifications` and surfaced only when non-empty (a "Signatures" button in the top bar), to avoid cluttering the UI for the common case of an unsigned document.
- A real pitfall hit writing the engine test: the first version flipped a byte at the file's literal midpoint to simulate tampering, and the test failed — the midpoint landed inside the `/Contents` hex-digit placeholder's unused trailing padding (PDFBox preallocates a fixed-size placeholder larger than the actual CMS bytes), which has no effect on the parsed signature at all. Fixed by tampering a byte near the start of the file instead, safely inside the signature's first byte-range segment. Worth remembering for any future test that tampers PDF bytes to simulate an attack: pick an offset inside a byte-range segment, not an arbitrary one.
- Not done in this increment (tracked in `planning/IMPLEMENTATION_BACKLOG.md`): certificate chain validation beyond the leaf, timestamping/revocation (still out of DEC-002's v1 scope), and any UI distinction for multiple signatures' relative ordering/coverage.

## ADR-016 — SEC-001 malformed-PDF corpus: hand-built parse-safety cases, not fuzz, not PdfRenderer
- Status: Decided (hardening increment, first pass).
- Decision: `MalformedPdfCorpusTest` is a small, deliberately hand-built corpus (8 cases) run only against `PdfBoxEditEngine` — the engine that actually touches untrusted documents for anything past baseline rendering (PDF-005/006/007/008 all go through it). Each case asserts the engine's `open()` call, and in one case downstream page-indexed operations, complete within a bounded `withTimeout` and never throw past `PdfOpenResult`/a plain boolean — not that the file is rejected with any particular error (several malformed inputs are things PDFBox's own recovery parser may or may not successfully salvage, and asserting a specific outcome there would be testing PDFBox's internals, not this app's safety boundary).
- Scope, stated explicitly rather than implied by omission: this is *parse-safety* testing (malformed/hostile structure must not hang, crash, or throw uncaught), not *memory-exhaustion/decompression-bomb* resistance. `docs/SECURITY_PRIVACY.md` §2 itself frames that harder problem as potentially needing process isolation or SDK-level sandboxing — neither exists in this app's current single-process architecture, and building either is a separate, much larger decision than a test pass. Marking SEC-001 "in progress" (not "Verified") in `docs/TRACEABILITY_MATRIX.md` reflects that this is real but partial coverage.
- Also explicitly not a true fuzz pass: the 8 cases are each a deliberate, understood scenario (empty file, non-PDF bytes, header-only, truncated, corrupted trailer/xref region, a self-referential page tree, an encrypted file opened without a password, a zero-page document), not randomly mutated/generated byte corpora. A real fuzz pass (e.g. libFuzzer-style mutation against the PDFBox parser) is a distinct, larger follow-up, tracked in `planning/IMPLEMENTATION_BACKLOG.md`.
- `android.graphics.pdf.PdfRenderer` (`PlatformPdfRendererEngine`) is deliberately **not** included in this corpus: Robolectric has no real binding for it in this toolchain (ADR-006) — `PdfRenderer.pageCount` reads back 0 regardless of input validity — so a "malformed-input test" against it under Robolectric would pass trivially without ever actually parsing the bytes. Writing that test would create the appearance of coverage that isn't real, which is worse than the gap being visible. Still needs a real device/emulator.
- A real finding while writing this, not a bug: the zero-page-document test (`aDocumentThatOpensButHasNoValidPagesRejectsPageOperationsSafely`) initially looked suspicious under Gradle's reported test duration (4.5–8.3s, close to the 5s-per-phase timeout budget), which could have indicated a genuine slow-path/DoS concern in PDFBox's page-tree recovery logic. Added temporary timing instrumentation to isolate it: the actual `open()`/`addNoteAnnotation()`/`rotatePage()`/`deletePage()` calls completed in under 100ms combined — the reported duration was Robolectric's own per-test sandbox/classloader startup overhead, not the code under test. Removed the instrumentation once confirmed; worth remembering that a Robolectric test's *reported* duration includes sandbox setup and isn't a reliable signal of the code's own performance on its own.

## ADR-017 — PDF-006 page-reorder UI: a "move to position N" dialog, not thumbnail drag-and-drop
- Status: Decided (backlog follow-up increment).
- Decision: `ReaderViewModel.movePageTo(targetPageNumber1Based)` + a `MovePageDialog` (plain numeric target, 1-based, opened from the existing "Page" menu) is how the user triggers `PdfEditEngine.movePage` — not dragging thumbnails in `ThumbnailStrip`, even though the backlog had originally framed the gap that way ("no drag-to-reorder on the thumbnail strip").
- Why not drag-and-drop, given it was the originally-imagined UI: `ThumbnailStrip` renders each thumbnail via `ReaderViewModel.pageBitmap(index, ...)`, which always asks [pdfEngine] (`PlatformPdfRendererEngine`, still pointed at the *original*, unedited file) to render page `index` — exactly the same reason delete/merge don't get a live preview (ADR-010/ADR-011). A drag gesture that visually reordered thumbnails without the underlying render changing would be actively misleading: the user would see thumbnail "A" move to position 3, but behind that thumbnail is still literally page-index-3's original bitmap, not page A's. Making drag-and-drop *actually* correct would require either (a) a second, purely-visual "display order" mapping that every page-indexed UI surface (thumbnail strip, continuous scroll, single-page nav, jump-to-page) would need to route through, decoupled from the real engine index — a change with much wider blast radius than "add a reorder control" — or (b) making the render engine follow the edit engine's order live, which reopens the exact two-engines-don't-share-state question ADR-010 deliberately avoided. Neither is worth it for what the feature actually needs to accomplish.
- A direct "move to position N" control sidesteps this entirely: it never claims a visual change that didn't happen. It reports the same staged "Page moved. Export a copy to save this change." feedback as delete/merge, so the user's mental model (this previews nothing until I export) stays consistent across all three page-structure operations rather than move behaving differently just because it happens to be easier to visualize as a drag.
- `movePageTo` takes a *target position*, not a from/to pair — the "from" is always `currentPageIndex` (the page currently being viewed), since that's simpler for the user to reason about ("move the page I'm looking at to position N") than picking two arbitrary pages from a strip.
- Not done in this increment: a genuine drag-and-drop reorder experience is still a real gap if that's ultimately wanted, but it would need the display-order-mapping work described above as its own, separate increment — not bundled into this one.

## ADR-018 — PDF-006 insert-at-position and extract-to-new-file
- Status: Decided (backlog follow-up increment).
- Decision: `PdfEditEngine.insertDocument(source, atIndex)` imports a picked document's pages (always appended to the end first — `PDPageTree` has no "insert at index" primitive, same constraint `movePage` already worked around, ADR-011) and then rebuilds the page order with the newly-imported pages spliced into `atIndex`, via the identical "convert to list, splice, remove-and-re-add everything" technique as `movePage`. Staged like merge/move: `pdfEngine` doesn't reflect it until export.
- `PdfEditEngine.extractPages(pageIndices)` is structurally different from every other PDF-006 operation: it **never touches the currently-open document**. It builds a brand-new `PDDocument()`, imports the requested pages (by value — `importPage` copies, it doesn't move/remove from the source), validates it the same way `writeValidatedTempCopy` does (save, reopen, confirm page count), and returns that as a temp file. Because nothing about the open document changed, there's no "stage it and tell the user to export" step for extraction — `ReaderViewModel.extractCurrentPageTo` writes the result straight to the user's chosen destination via the existing `DestinationWriter`, same immediate commit shape as `exportAnnotatedCopy`/`finishSigning`, just triggered by a different source engine call.
- UI scope, deliberately narrower than the engine: `extractPages` takes a list of page indices (so a future multi-page-range extraction needs no engine change), but the "Extract this page…" menu entry only ever calls it with the single currently-viewed page. Building a multi-select UI (checkboxes on the thumbnail strip, a range picker) is real additional work with its own design questions (how to show a multi-page selection without conflicting with the existing single-tap-to-jump thumbnail interaction) that didn't belong bundled into this increment — tracked as its own backlog item.
- Insert's position dialog (`InsertPositionDialog`) accepts `1..pageCount + 1` (the `+1` means "after the last page," equivalent to appending) — same 1-based-position convention as `MovePageDialog` (ADR-017), for a consistent mental model across the two dialogs the user sees in the same "Page" menu.
- Not done in this increment (tracked in `planning/IMPLEMENTATION_BACKLOG.md`): multi-page-range extraction UI, and any visual (not just numeric) indication of where an insert position falls relative to the thumbnail strip.

## ADR-019 — PDF-010 print: hand the existing validated temp copy to PrintManager unmodified
- Status: Decided (backlog follow-up increment). **Not yet build/test-verified** — see caveat below.
- Decision: `ReaderViewModel.requestPrint(documentName)` calls the exact same `PdfEditEngine.writeValidatedTempCopy()` already used by `exportAnnotatedCopy` — one validated temp file, with any staged annotations/page-ops/stamps applied, reused for both "export a copy" and "print." A new `PrintState` (`Idle`/`Preparing`/`Ready(file, documentName)`/`Failure`) tracks that preparation, mirroring `ExportState`'s shape.
- `PdfPrintDocumentAdapter` (`app/src/main/java/com/pdfreader/app/print/`) does no rendering of its own: `onWrite` streams the temp file's raw bytes straight to the print framework's destination file descriptor, and `onLayout` declares `PAGE_COUNT_UNKNOWN`/`CONTENT_TYPE_DOCUMENT` so Android's own print spooler parses the PDF itself. This only works because the temp file is already a complete, valid PDF — there is nothing to lay out or paginate on this app's side.
- Why `MainActivity`, not `ReaderScreen`, calls `PrintManager.print(...)`: every other platform/OS-level action in this app (SAF pickers, `ACTION_CREATE_DOCUMENT`) is invoked from `MainActivity` via `registerForActivityResult`, with `ReaderScreen` staying pure UI-plus-callbacks. Print has no activity-result callback (the system print dialog's outcome never comes back to the app), but keeping the actual `getSystemService(PrintManager::class.java)` call in `MainActivity` (a `LaunchedEffect` watching `printState` inside `setContent`) keeps that one architectural boundary consistent rather than reaching for `LocalContext` inside `ReaderScreen` just for this one feature.
- Cleanup: the temp file is deleted in `PdfPrintDocumentAdapter.onFinish()`, not right after handing it to `PrintManager.print()`. The user can sit in the system print dialog for an arbitrary amount of time before `onWrite` is ever called (or never call it at all, if they cancel) — `onFinish()` is the only lifecycle point the framework guarantees will fire once the adapter is truly done.
- **Caveat, unlike every other ADR in this file**: this increment was implemented on a machine with no JDK/Android SDK installed, so there is no `./gradlew assembleDebug`/`testDebugUnitTest`/`lintDebug` evidence for it — it has not been compiled, let alone unit-tested or run through a real print dialog on a device/emulator. Treat this as unverified until a build/test pass (and real-device print verification) happens on a machine with the toolchain available.
- Not done in this increment: progress/cancellation feedback beyond the system print dialog's own UI, and any test coverage (`PdfPrintDocumentAdapter` is a thin platform-API shim with no Robolectric binding for `PrintManager`, similar to the `PlatformPdfRendererEngine` gap in ADR-006).
