## Phase 3 — Annotations and page operations (engine approved, first annotation increment done)
- [x] **PDF-engine proof of concept** (`docs/ARCHITECTURE.md` §2): PDFBox-Android (Apache-2.0) evaluated and POC-tested — annotate/save/reopen round trip, merge, and encrypted-PDF open/reject all pass (`app/src/test/java/com/pdfreader/app/poc/PdfBoxAndroidEnginePocTest.kt`, 3/3 tests). **Approved as DEC-001** (`docs/DECISIONS_AND_OPEN_QUESTIONS.md`) by the user on 2026-10-30. Dependency promoted from `testImplementation` to `implementation`.
- [x] `PdfEditEngine`/`PdfBoxEditEngine` adapter: open, add a text-note annotation, count annotations, write-validated-temp-copy. `PdfBoxEditEngineTest` exercises it directly (not just the gate-evidence POC).
- [x] Minimal annotation UI: "Annotate" mode toggle (disables pinch-zoom while active, by design — see planning/ADR.md ADR-010), tap-to-place a note, Compose `Canvas` overlay markers, "Export copy" action using `ACTION_CREATE_DOCUMENT` (never overwrites the original) with a Saving/Success/Failure banner. — PDF-005, PDF-010
- [ ] Annotation types beyond a plain text note (highlight/underline/strike/pen/eraser/textbox/shapes). — PDF-005
- [ ] Undo/redo and annotation deletion — not implemented; currently annotations can only be added, never removed, within a session.
- [ ] Custom note text entry (currently always "Note" — no text-input dialog yet).
- [ ] Annotating in continuous-scroll layout (currently single-page-mode only).
- [x] Rotate (quarter-turn, live visual feedback via a Compose rotation — no re-render needed), delete, move/reorder, and append/merge (pick another PDF, appended to the end) implemented in `PdfEditEngine`/`PdfBoxEditEngine`; rotate/delete/merge wired into a "Page" menu in the UI. `PdfBoxEditEngineTest` covers all four against the real engine. — PDF-006
- [x] Reorder/move UI: a "Move this page…" entry in the "Page" menu opens a dialog asking for a 1-based target position, calling `ReaderViewModel.movePageTo`. Not drag-and-drop on the thumbnail strip — see `planning/ADR.md` ADR-017 for why that would be misleading given the staged-edit architecture (the thumbnail strip renders from the unedited file via `PdfEngine`, which a move doesn't touch, so dragging a thumbnail wouldn't visually move anything).
- [ ] Insert-at-position and extract-to-new-file not implemented (`appendDocument` only adds to the end; there's no "extract selected pages into their own file").
- [ ] No preview, progress, or cancellation for merge/delete/rotate — they apply immediately and silently stage the change (a snackbar says so), which is fine for a 1-3 page fixture but will matter for larger real documents.
- [ ] Page-structure changes (delete/move/merge) are staged only — the live render stays on the unedited file (via `PdfEngine`) until the user exports a copy. This is a known, documented limitation (planning/ADR.md ADR-010), not an oversight, but a "preview after merge/delete" experience would need the render engine to pick up the edited document somehow.
- [x] Malformed-PDF corpus pass against PDFBox-Android (`app/src/test/java/com/pdfreader/app/security/MalformedPdfCorpusTest.kt`, SEC-001) — 8 hand-built malformed/adversarial fixtures (empty, non-PDF, header-only, truncated, corrupted trailer/xref, self-referential page tree, unencrypted-open of an encrypted PDF, zero-page document), all confirmed to open without hanging or throwing past `PdfOpenResult`, and to reject page-indexed operations cleanly on a pathological document. Scope is parse-safety only — see the two items below for what this does *not* cover.
- [ ] True decompression-bomb/memory-exhaustion resistance is not covered by the above — docs/SECURITY_PRIVACY.md §2 itself frames that as possibly needing process isolation/sandboxing, which this app's current single-process architecture doesn't have. A real "fuzz" pass (randomized/mutated byte corpora, not just hand-built cases) is also not done — the corpus above is small and deliberately targeted, not generated.
- [ ] `android.graphics.pdf.PdfRenderer` (`PlatformPdfRendererEngine`) has no malformed-input test coverage at all — Robolectric has no real binding for it (ADR-006), so nothing here can exercise it; needs a real device/emulator.
- [ ] BouncyCastle is now transitively present (via PDFBox-Android — confirmed via `./gradlew :app:dependencies`, see `planning/DEPENDENCY_LICENSE_INVENTORY.md`) but has not been separately vetted for direct use signing PDFs (PDF-008) — still a distinct, gated piece of work.

## Phase 4 — Signature workflows (visual signature done; digital signature sign+validate implemented, device-level verification pending)
- [x] Visual signature draw/type/import, placement, private local storage, excluded from sync by default. — PDF-007. **Not gated** like PDF-008: `docs/DECISIONS_AND_OPEN_QUESTIONS.md` only requires a decision before *certificate-based* signing, and a visual signature is just a stamped image, which the already-approved PDFBox-Android engine (DEC-001) can do directly — no new engine/library decision needed. `LocalFileSignatureRepository` stores signatures as PNGs under app-private `filesDir` (never SAF, never a content provider); `android:allowBackup="false"` (already set, `AndroidManifest.xml`) covers "excluded from sync by default" without needing a separate `dataExtractionRules.xml` (that stays a cross-cutting lint item below, since it only matters once `allowBackup` is ever turned on). Draw (finger strokes), type (rendered text), and import (picked image, downscaled to at most 800px) are all implemented, behind a "Sign" menu in `ReaderScreen.kt`. Placing a signature calls `PdfEditEngine.addImageStamp` and also adds a live Compose overlay (same pattern as note annotations, PDF-005) — see `planning/ADR.md` ADR-012.
- [ ] Imported signature images are not background-removed/trimmed — a photo of a signature on paper will stamp with its paper background intact. — PDF-007
- [ ] No undo for a single placed signature stamp (whole-document "don't export this" is the only way back, same limitation as PDF-006's staged edits).
- [ ] No per-document remembered placement/size — every placement defaults to 35% of page width at the tapped point.
- [ ] Recovery of saved signatures across device changes/reinstalls (an explicit open question in `docs/DECISIONS_AND_OPEN_QUESTIONS.md`) is unaddressed — purely local storage has no backup/recovery story yet, and won't until Phase 5 (cloud sync) is designed.
- [x] **Gate passed**: digital-signature profile approved as DEC-002 (`docs/DECISIONS_AND_OPEN_QUESTIONS.md`, 2026-10-30) — PAdES-B-B, both Android-Keystore-self-signed and PKCS#12-import as separate key-source flows, no timestamping/revocation checking in v1 (disclosed limitations).
- [x] Signing-engine POC: `PdfSignaturePocTest` signs a fixture via PDFBox-Android's external-signing hook (`addSignature`/`saveIncrementalForExternalSigning`) + BouncyCastle's CMS API (`CMSSignedDataGenerator`), verifies the signature against the actual signed content, and detects a single tampered byte. 1/1 test passing. **Real finding from this POC**: a test-classpath-only BouncyCastle version collision (Robolectric's own `bcprov-jdk18on` transitive dependency vs. PDFBox-Android's `bcprov/bcpkix-jdk15to18:1.72`) caused `NoSuchFieldError` — fixed by excluding the `jdk18on` artifacts from the `testImplementation(libs.robolectric)` dependency in `app/build.gradle.kts` (confirmed not present on the production `debugRuntimeClasspath`).
- [x] `PdfEditEngine.signWithDetachedCms` + `PdfBoxEditEngine` implementation (PDF-008): signs a snapshot of the live document (not the live document itself — see `planning/ADR.md` ADR-014), via PDFBox's external-signing hook + BouncyCastle CMS. Validated (reopen, confirm page count and a real signature dictionary) before being returned, same contract as `writeValidatedTempCopy()`.
- [x] Two separate, separately-tested signing-key-source flows (DEC-002), each its own small package under `app/src/main/java/com/pdfreader/app/signing`: `AndroidKeystoreSigningIdentityManager` (device-bound, hardware-backed self-signed identities — real "AndroidKeyStore" provider, cannot be unit-tested, no real Keystore under Robolectric) and `BouncyCastlePkcs12SigningMaterialLoader` (imported .p12/.pfx, decrypted only in memory, real unit test via an in-memory-built PKCS#12 file — resolves the "verify exact Android API level" gap by using this project's own bundled BouncyCastle provider for PKCS12 parsing instead of depending on Android's own, per ADR-014).
- [x] Signing UI: a "Digitally sign" menu in `ReaderScreen.kt`, deliberately separate from the "Sign" (visual signature, PDF-007) menu — create/select/delete a Keystore identity, or pick a .p12 file and enter its password, then pick a destination to save the signed copy. Carries the DEC-002-required disclosure ("no revocation or timestamp checking in this version") as a disabled menu header, same pattern as PDF-007's "appearance only" disclaimer.
- [ ] Real-device verification (Android Keystore has no real backing under Robolectric — only `PdfBoxEditEngine`'s CMS mechanics and the PKCS#12 loader have real unit test coverage; the Keystore identity flow is covered only by a fake). Not verified: whether a signed PDF actually displays as "signed" (even if untrusted) in a real-world PDF viewer like Adobe Acrobat.
- [x] PDF-008's "validate" half: `PdfEditEngine.verifySignatures` checks every signature already in an opened document (cryptographic consistency against the embedded certificate + certificate expiry window), by re-reading the source's raw bytes rather than trusting a PDFBox re-save (which could reformat and break byte-range checks — see `planning/ADR.md` ADR-015). A "Signatures" status button/dialog in `ReaderScreen.kt` shows each result, with the required disclosure that trust-anchor/revocation/timestamp are not checked. Covers only self-consistency, never "trusted" — deliberately, per DEC-002.
- [ ] No certificate CHAIN validation (intermediate → root) — only the leaf certificate embedded alongside the signature is checked for expiry; a chain with an expired/revoked intermediate is not detected.
- [ ] No timestamping (RFC 3161) or revocation (OCSP/CRL) checking — explicit, disclosed v1 limitations per DEC-002, not a gap to silently close later without another decision.
- [ ] Multiple signatures on one document are verified independently but the UI doesn't explain *order* (e.g. a later signature invalidating an earlier one's "covers entire document" claim) beyond the per-signature `coversEntireDocument` flag.
- [ ] Imported PKCS#12 certificates are not previewed (subject/expiry) before signing — the password dialog has no "this is the certificate for Jane Doe, expires 2027" confirmation step.
- [ ] No UI indication of a signing identity's own expiry (self-signed certs are created with a ~100-year validity in `AndroidKeystoreSigningIdentityManager`, so this mostly matters for imported PKCS#12 certs with a real, shorter expiry).
