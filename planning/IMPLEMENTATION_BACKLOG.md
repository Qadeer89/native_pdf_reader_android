- [x] Imported signature images are now background-removed: `removeLightBackground` (`data/signatures/SignatureBackgroundRemoval.kt`) makes near-white/light pixels transparent (feathered luminance threshold — no ML segmentation), applied automatically in `ReaderViewModel.importSignatureImage` (drawn/typed signatures already have a transparent canvas, so they're untouched). — PDF-007

- [x] **Gate passed**: digital-signature profile approved as DEC-002 (`docs/DECISIONS_AND_OPEN_QUESTIONS.md`, 2026-10-30) — PAdES-B-B, both Android-Keystore-self-signed and PKCS#12-import as separate key-source flows, no timestamping/revocation checking in v1 (disclosed limitations).

- [x] `PdfEditEngine.signWithDetachedCms` + `PdfBoxEditEngine` implementation (PDF-008): signs a snapshot of the live document (not the live document itself — see `planning/ADR.md` ADR-014), via PDFBox's external-signing hook + BouncyCastle CMS. - [x] Signing UI: a "Digitally sign" menu in `ReaderScreen.kt`, deliberately separate from the "Sign" (visual signature, PDF-007) menu — create/select/delete a Keystore identity, or pick a .p12 file and enter its password, then pick a destination to save the signed copy. Carries the DEC-002-required disclosure ("no revocation or timestamp checking in this version") as a disabled menu header, same pattern as PDF-007's "appearance only" disclaimer.
- [x] Certificate chain validation (still DEC-002-scoped, not a new decision): `PdfBoxEditEngine.validateCertificateChain` walks a signature's own embedded CMS certificate chain (subject/issuer matching + `cert.verify`) and reports it via `SignatureVerificationResult.chainValid`, shown in the "Signatures" status dialog. Explicitly not trust-anchor/root-CA validation (no app-curated trust store), not revocation (OCSP/CRL), not timestamping — all three stay out of scope per DEC-002 until a separate future decision; the UI discloses this next to the result.
- [ ] Real-device verification (Android Keystore has no real backing under Robolectric — only `PdfBoxEditEngine`'s CMS mechanics and the PKCS#12 loader have real unit test coverage; the Keystore identity flow is covered only by a fake). - [x] PDF-008's "validate" half: `PdfEditEngine.verifySignatures` checks every signature already in an opened document (cryptographic consistency against the embedded certificate + certificate expiry window), by re-reading the source's raw bytes rather than trusting a PDFBox re-save (which could reformat and break byte-range checks — see `planning/ADR.md` ADR-015). A "Signatures" status button/dialog in `ReaderScreen.kt` shows each result, with the required disclosure that trust-anchor/revocation/timestamp are not checked. Covers only self-consistency, never "trusted" — deliberately, per DEC-002.
- [ ] No certificate CHAIN validation (intermediate → root) — only the leaf certificate embedded alongside the signature is checked for expiry; a chain with an expired/revoked intermediate is not detected.
- [ ] No timestamping (RFC 3161) or revocation (OCSP/CRL) checking — explicit, disclosed v1 limitations per DEC-002, not a gap to silently close later without another decision.
- [ ] Multiple signatures on one document are verified independently but the UI doesn't explain *order* (e.g. a later signature invalidating an earlier one's "covers entire document" claim) beyond the per-signature `coversEntireDocument` flag.
- [ ] Imported PKCS#12 certificates are not previewed (subject/expiry) before signing — the password dialog has no "this is the certificate for Jane Doe, expires 2027" confirmation step.
- [ ] No UI indication of a signing identity's own expiry (self-signed certs are created with a ~100-year validity in `AndroidKeystoreSigningIdentityManager`, so this mostly matters for imported PKCS#12 certs with a real, shorter expiry).
